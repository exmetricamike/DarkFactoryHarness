# Lessons — what previous nights taught this harness

Cross-project memory. **This file is not project-specific and never leaves the harness repo** —
it travels to the next project, `active-project/` does not. Read it at the start of every phase command;
it is kept short on purpose.

## How to write a lesson

One line, in the phase section it applies to:

```
- **L-012** <the rule, imperative, general> ⟨<generic project shape>; <what it cost>⟩ hits:3 conf:high
```

- **Rule** — must be actionable on a project this harness has never seen. "Paste the real route
  signatures into the frontend prompt" is a lesson. "The `/orders` endpoint returns a cursor" is not.
- **Context in ⟨⟩** — the *shape* of the project it came from, never its identity: no client or product
  names, no repo paths, no proprietary domain terms. "a fintech dashboard SPA (React + FastAPI)",
  "a multi-tenant billing backend (Django)", "an internal ops tool with no test suite". Plus what the
  incident actually cost — fix rounds, a reverted WP, an hour of the night.
- **hits** — times this lesson has been applied or re-confirmed since it was written. Bump it when it fires.
- **conf** — `high` (seen on ≥2 projects, or once with unambiguous evidence) · `med` (once, clear cause)
  · `low` (a hunch that earned a line; delete it if the next project does not confirm it).

## How to keep it useful

- **Ceiling: 30 lessons.** Adding the 31st means merging two or deleting the weakest — lowest `hits`,
  oldest, or superseded. A file nobody can read at 2am teaches nothing.
- **Contradicted by experience → rewrite or delete it.** Do not stack a counter-lesson on top of a
  wrong one; there is one current answer per situation.
- **Graded by the user → that grade wins** over your own reading of the night.
- Never record here what belongs in `active-project/` (a decision about this product, a repo quirk,
  a WP follow-up). This file only holds things that will still be true on the next project.

## spec
- **L-001** Before writing a numeric budget, row-count, or capacity assumption into a spec, verify it against the real current state (actual query sites, actual seeded row counts) — don't carry it forward unchecked from an earlier planning document. ⟨a multi-night unattended full-stack rebuild, Django/DRF + Next.js; 2 review rounds and one spec written against a fixture with zero rows in the domain it described⟩ hits:1 conf:med
- **L-002** When a spec states a global constraint, name its exemptions in the same sentence — a rule and its exception stated separately will contradict each other the moment someone reads only one of them. ⟨same project shape; one review round spent resolving a spec that both banned and required the same thing⟩ hits:1 conf:med
- **L-003** After amending a spec in response to review, grep the whole document for the value you just changed — a fix applied in one place often leaves the old literal standing in three or four others. ⟨same project shape; a full extra review round caused entirely by the coordinator's own leftover literals⟩ hits:1 conf:med
- **L-004** When a spec needs an exact formula whose correctness depends on a library's internal semantics (e.g. where a chart scale maps a category to a pixel), state the intent in words and let implementation/browser verification settle the arithmetic — don't pin a formula built on an assumption about the library that might be wrong. ⟨same project shape; a wrong pixel formula was implemented faithfully and reproduced a defect three prior review rounds had already removed⟩ hits:1 conf:med
- **L-005** Treat an approved design mock's own copy/microcopy as a claim to verify against the data model, not text to paste verbatim — a mock can assert something ("every figure is last month's") the underlying data cannot actually guarantee. ⟨same project shape⟩ hits:1 conf:med

## build
- **L-006** When a permission/guard class is only ever reached through a route gated by an even stricter check, no route's own test can exercise it — write a direct unit test against the guard class itself. ⟨same project shape⟩ hits:1 conf:med
- **L-007** When a feature adds a backwards or relative lookup keyed by date/index (e.g. reading `period − 1`), re-audit every other lookup keyed by the same axis — the new read can make a previously-unreachable gap reachable on day one. ⟨same project shape⟩ hits:1 conf:med
- **L-008** A dev server left running from earlier in the session does not necessarily reflect code a later implementer round just wrote — restart it and hit a live endpoint before trusting its response, especially across fix rounds or resumed sessions. ⟨same project shape; caused two false "still broken" verification results in one night before the server was restarted⟩ hits:2 conf:med

## verify / run
- **L-009** When an acceptance check bans something a later, already-planned WP will legitimately introduce, narrow the assertion to name the WP that sanctions the exception rather than letting a correct future change fail an old check. ⟨same project shape⟩ hits:1 conf:med
- **L-010** Automated fixtures and e2e suites typically only ever exercise one seeded, happy-path state. Deliberately drive at least one out-of-fixture state (an empty/unpopulated period, an un-seeded parameter) as part of every UI WP's verification — this is where real defects hide that a green suite walks straight past. ⟨same project shape; a real display defect (a parent row and its child rows making contradictory claims about the same absent data) was caught only this way, after every automated check had passed⟩ hits:2 conf:med
- **L-011** If a frontend auto-attaches a bearer token to every request, exclude public/auth endpoints (register, login, password reset) from it explicitly, and verify by testing with a deliberately stale/invalid token already in storage — not just a clean session — since an auth-gated framework can 401 a public endpoint before its own permission check ever runs, permanently locking a user out. ⟨same project shape⟩ hits:1 conf:med
- **L-012** A green run does not prove the code path under test actually executed — a test can silently skip when its dependency is absent, a REPL can swallow an error and still hit a later print statement, or a check can be structurally incapable of failing. Mutation-test any new verification script once (break the thing it's supposed to catch, confirm it goes red) and confirm the services it depends on were actually live, before trusting a PASS from it. ⟨same project shape; caught a script that reported "ALL PASS" on a section that could never have failed, and a shell-piped script that silently swallowed errors after an unblanked line and still printed success⟩ hits:2 conf:med

## coordination (backend, budget, continuity)
- **L-013** Commit each WP once it's independently verified before starting the next build in the same repo — starting the next build on top of an uncommitted previous one mixes two WPs into one working tree and can make one WP's failure look like it belongs to the other. ⟨same project shape⟩ hits:1 conf:med
- **L-014** Never fully overwrite a persistent log/memory file that is the only record of past work (especially one that lives outside version control) — always append/edit it. An overwrite where an edit was meant destroys history with no way back. ⟨same project shape; a WP's own review-round history was permanently destroyed this way⟩ hits:1 conf:med
- **L-015** When a spec review needs to verify a contract (an API shape, a serializer's fields) that lives in a different repo than the one being changed, give the reviewer read access to the repo that owns the contract, not just the one being modified — otherwise a factual claim about the other side of the boundary goes unverified. ⟨same project shape; found a BLOCKER (a serializer silently dropping a field) only because the reviewer could read the other repo, then reused the same setup deliberately on the next WP⟩ hits:1 conf:med
- **L-016** When polling an agent's log file for a completion sentinel, match the concrete value you expect, not a line shape that could also appear in the prompt's own echoed template — a prompt that shows the required output format can itself satisfy a loose match. ⟨same project shape⟩ hits:1 conf:med
- **L-017** A CLI tool's flag compatibility can differ between its subcommands (e.g. a `resume`/`fork` subcommand vs. the main command) and can change between minor versions. Re-check `--help` for the exact subcommand you're calling — especially right after noticing a version bump — rather than assuming a previously-working invocation still works. ⟨same project shape; hit twice in one project as the CLI moved versions mid-run⟩ hits:2 conf:med

## Candidates — this project, not yet distilled

Appended during the night, cheap and unfiltered. `/df-retro` promotes, merges or drops every
line here and leaves the section empty. Anything still sitting here at the start of a new
project is dropped — an undistilled candidate is noise, not memory.

- When an intake document names both a design mock and a backend validation schema as "authoritative" for the same form, diff their fields one by one before writing the spec — they routinely disagree, and the contradiction is invisible until you read both. ⟨a mobile extension of a shipped app, KMP + Express/Firestore; caught at intake, would have been a reverted WP⟩
- Verify an intake document's claims about which endpoint does what against the route files before speccing against them — a plausible-sounding endpoint name can belong to something else entirely, and a "feature flags" endpoint can turn out to return one unrelated platform toggle. ⟨same project shape; two of five intake open items were factually wrong about the code⟩
- cand: `codex exec --approve-for-me` stopped accepting `-s/--sandbox` in a CLI minor bump (0.152→0.154), failing exit 2 on the first call of the night — re-run `--help` for the exact invocation after any version change, not just for subcommands (confirms L-017 a third time). ⟨cross-repo mobile+backend night; one wasted call⟩
- cand: reading the auth layer before speccing showed the client's cookie jar was in-memory while the spec claimed encrypted persistence — grounding a "session restore" WP in the storage implementation, not the spec's prose, caught a feature that had never actually worked. ⟨KMP client + Express/Firestore backend; would have shipped a WP whose acceptance criterion was untestable⟩
- cand: the target repo's own test suite was 32/53 suites red before any work started — measure the suite's baseline in a clean worktree at the pre-WP sha before judging a WP by it, or you will chase failures you did not cause. ⟨Express/TypeScript backend with native-module test deps; ~10 min, but it made every later verification unambiguous⟩
- cand: verifying auth end to end needs a real credential, and the obvious route (the product's own registration endpoint) was captcha-gated even on dev — budget for a scripted account-creation path against the dev project, and log the accounts you create so the user can delete them. ⟨marketplace backend with Firebase Identity Platform; would otherwise have shipped a WP verified only on 401 paths⟩
- cand: a spec that mandates a blanket quality threshold (WCAG AA, a latency budget, a bundle size) against values it does not itself compute will contradict the supplied design — compute the metric for every supplied value while writing the spec, and record the measured table plus explicit exceptions instead of the rule alone. ⟨mobile app adopting an approved design token set; the implementer refused the WP outright, one wasted implementation call, and two real accessibility failures in the approved palette surfaced only here⟩
- cand: when the implementer refuses a frozen spec as self-contradictory, verify its arithmetic independently before amending — it was right twice tonight, and the independent recomputation is what produced the corrected table rather than a patch of the one value it complained about. ⟨same project shape⟩
- cand: when a review round amends a spec, re-read the amended file and grep for every term the amendment renamed — three of the next round's blockers were stale references the amendment itself created (a field renamed in one section, still asserted in the acceptance criteria and required tests). Confirms L-003 on a second project shape. ⟨cross-repo mobile WP; one extra review round each time⟩
- cand: a scripted spec amendment that asserts before writing can fail silently into the next step — the prompt was rebuilt from the unamended file and the reviewer returned a verbatim-identical issue list, which reads exactly like the model repeating itself. Make the amend step and the prompt-build step fail loudly together, or verify the prompt contains the new text before sending. ⟨same project shape; one wasted review call⟩
- cand: verify the repo is on the branch the work package targets before every spec review round, not just at the start of the WP — a repo found sitting on its mainline had none of the feature layer the spec built on, so three review rounds read a tree that could not contradict the spec. One `git branch --show-current` per round. ⟨cross-repo mobile+backend night; two extra review rounds⟩
- cand: an agent's sandbox root is fixed when its session is created, so a work package spanning two repos needs one session per repo — a resumed session reported it "could not write" the second repo rather than failing loudly, which reads like a refusal to work. Inline the first repo's real contract into the second prompt and the fresh session loses nothing. ⟨same project shape; one wasted implement call⟩
- cand: when a design system's tokens are ground-specific (a light card on a dark page), an implementer will reach for the wrong half and the compiler will not care — invisible text ships. Name the ground in the token's own comment, and verify every new screen on a real device, not only by its unit tests: a button rendered white-on-white was caught by nothing else. ⟨mobile app on an approved dark palette; two real defects, both invisible to a green suite⟩
- cand: a test that asserts on a `stateIn`/derived flow's `.value` before its collector has started reads the initial value forever — it fails for a reason that has nothing to do with the code under test, and the obvious "fix" is to weaken the assertion. Start the collector and advance the scheduler before dispatching anything. ⟨KMP/Compose MVI; three red tests that blamed the wrong layer⟩
- cand: a framework registry that is not a compile-time construct (a serializers module, a DI graph, a route table) is where an implementer's work silently comes apart — the code compiles, the tests pass, and it dies on first navigation. Enumerate every such registry in the spec by file, and grep them after implementation. ⟨same project shape; two missed registrations, one of them missing an annotation every sibling had⟩
- cand: when a spec pins an exact parse of a URL, path or identifier, run that parse once in the real library before freezing it — a deep-link scheme's authority is not part of its path, and the wrong guard shipped a feature that silently ignored every link and a test that hung to its timeout instead of failing an assertion. ⟨mobile OAuth deep link, KMP + Ktor; one build round and a minute per test run⟩
- cand: paste the **implemented** contract into the second repo's prompt, read out of the committed code rather than copied from the spec — the spec is what you intended, the code is what the other side must match, and the gap between them is exactly where cross-repo WPs break. ⟨cross-repo mobile+backend night; no rework, which is the point⟩
- cand: a coordinator check script that builds a URL by hand must encode every value it interpolates — a config value containing `&` truncated the query and produced a convincing false failure that looked exactly like a product bug. Encode first, then debug the product. ⟨OAuth state with punctuation; ~10 minutes chasing the wrong layer⟩
- cand: a repository `update` that copies an explicit allowlist of keys will swallow any new field silently — the entity, the DTO and the serializer all look right, every unit test that stops at serialization passes, and nothing is written. When adding a field, grep the persistence layer for the *sibling* field's name and count the places it appears. ⟨Express/Firestore with hand-rolled DAO mapping; caught in spec review, would have been a green WP that wrote nothing⟩
- cand: an implementer will ship the wire value as the user-facing label (`LAWYER`, `ON_SITE`, `actively_looking`) unless the spec gives the exact copy for every enum it names — and no test catches it, because tests assert the wire value. Put the label table in the spec next to the value table, and always read the screen on a device. ⟨mobile onboarding over a typed API; five screens of raw enum values, one extra fix round⟩
- cand: a dev server with a file watcher will restart under a running live check when the implementer writes files, producing connection errors and stale-auth responses that look exactly like product defects. Run the definitive check against a server started without the watcher. ⟨Node/Express with nodemon; ~15 minutes chasing four phantom failures⟩
- cand: when a flow is one-way (onboarding, activation, a first-run migration), every live re-run needs a fresh fixture account — budget the creation script into the check itself rather than reusing one and reading the second run's failures as regressions. ⟨marketplace onboarding; one confusing re-run⟩
- cand: an idempotency key makes a *write* safe but not a *send* — the notification, the echo, the webhook all fire again on retry. Make the handler read-then-branch inside one transaction and gate every side effect on "did this call actually create it", and assert the side-effect count, not just the row count. ⟨chat send path over Firestore; found in review, would have double-notified every retry⟩
- cand: a document-store `orderBy` silently **excludes documents missing that field**, so an ordered list quietly hides exactly the newest records if the creating path does not write the sort key. Check what the create path actually writes before ordering by anything. ⟨Firestore conversations; the existing production query was already hiding brand-new rows⟩
- cand: when a spec-amendment script asserts before writing, a stale anchor aborts it and the *unamended* text goes to the reviewer, who then repeats their previous findings verbatim — which reads exactly like a model looping. After every scripted amendment, grep the document for the new text before sending, and treat a verbatim-repeated review as a tooling failure until proven otherwise. Confirms an existing candidate on a second project. ⟨long spec review; one wasted round and a misdiagnosis⟩
- cand: prefer replacing a whole anchored line or block over matching a long paragraph when scripting edits to prose — long anchors break on every earlier edit and on any non-ASCII the shell mangles, and each break costs a round. ⟨ten-round spec review; three aborted scripts⟩
- cand: a boolean query parameter mapped into a filter flag is a coin flip an implementer loses about half the time, and unit tests written over a mocked service never see it - the default list returned only the archived rows and every acceptance criterion downstream of "is it in the list" failed at once. Assert the parameter-to-argument mapping in the controller test, and read the first live failure as one bug rather than ten. <chat conversation list over Express; ten check failures, one cause>
- cand: an implementer with no compiler and no device ships UI as a placeholder - bare framework widgets, no polling, no empty/error states, no dialog the spec spent paragraphs on - while reporting the work package done. Verify a frontend WP by driving the built app, and budget one fix round per screen-bearing WP with the acceptance criteria quoted back verbatim. <KMP/Compose chat over a REST API; one full fix round, ten distinct gaps>
- cand: a DTO written from the reference implementation's payload will not match the new API's payload even when both are correct - the web nested job under an object, the mobile surface returns it flat, and the field silently stayed null through the mapper, the ViewModel and the screen. Check every DTO field against a real captured response body from the endpoint it actually calls. <mobile chat DTO vs /m/ API; job title missing everywhere, invisible to every test>
- cand: raw ISO instants reaching the screen are the default outcome when the domain model carries time as a String - nothing in the type system objects and no unit test reads like a defect. If a model carries formatted-for-nobody strings, the spec must name the display form for each surface. <mobile chat; caught only by looking at the device>
- cand: a poll that writes its failure into the same error field the first load uses will blank a screen that already has content on the first network blip. Keep the retry state for "nothing loaded yet" and let a refresh failure be a line above content that stays. <4 s chat poll; found by reading the branch, not by any test>
- cand: a test suite that is configured out never announces itself - the modules printed a one-line warning during an unrelated task listing and no build ever failed, so four work packages shipped tests that had literally never executed. Before trusting any test a work package ships, run the suite once and make it fail on purpose. <KMP multi-module app; six modules silently skipped, three real defects found the moment they ran>
- cand: a UI-tree dump is not ground truth for a declarative-UI overlay - `uiautomator dump` reported the deck card while a full-screen Compose match celebration was actually on screen, and the feature was declared broken twice before a screenshot showed it working. Verify overlays and anything drawn above the content with a screen capture, and keep the dump for coordinates. <KMP/Compose on an Android emulator; two false defect diagnoses, ~20 minutes>
- cand: any assertion about a timed UI affordance (a snackbar, a toast, an auto-dismissing banner) must be in the same shell command as the tap that triggers it - model latency between two tool calls is longer than the affordance's lifetime, so the tap lands on whatever is underneath and the feature reads as dead. <emulator undo snackbar, 4 s timeout; one false failure>
- cand: a replay-0 `SharedFlow` collected into a list from a test's background scope registers as a subscriber but never runs its lambda under a virtual-time scheduler, so the event is consumed and the list stays empty - a failure that looks like the production code never emitted. Await one-shot events (`async { flow.first() }`) instead of collecting them, and copy the pattern the repo already uses. <KMP MVI ViewModel tests; two red tests blaming the wrong layer>
- cand: a scoring engine that stores weighted contributions rather than sub-scores will be read as percentages by the first surface that displays a breakdown - a perfect match renders as four near-misses and no test objects, because the numbers are real. When a spec puts an internal metric on a screen, pin the rescaling function by name. <spec review caught it before implementation; the codebase had a `getDimensionPercent` nobody would have found>
- cand: an implementer told to delete a "legacy" file will take every declaration that happens to live in it, including the three still-used types the file also held - the build breaks in a module nobody touched. Before accepting a delete, grep the deleted file's exported symbols, not just its obvious ones. <cross-repo mobile WP; three compile errors, five minutes, but they would have read as a broken WP>
- cand: verifying a "counter agrees with its list" acceptance criterion against an account whose lists are all empty is a 0 == 0 tautology that passes everything - seed real rows through the product's own write endpoints before judging any agreement assertion. <activity counters over a dev account with no history; the first green run proved nothing>
- cand: when another person's dev server holds the port the app is hardcoded to call, run the verification backend on a second port and rebuild the client with that base URL rather than stopping their process - and revert the constant before committing. Killing it may also simply be refused by the harness's own policy. <shared Windows dev box, two developers, one port; ~10 minutes, no disruption to them>

- cand: a coordinator amendment made in response to review is itself a source of new review findings - two of the next round's issues were wording my own patch had left inconsistent (a count restated in four places, a bound reworded in one section but not the other). After every amendment, grep the document for the number and the phrase you just changed. Confirms L-003 on a third project shape. <four-round spec review; one extra round>
- cand: a concurrency assertion must name the thing being bounded - "no more than five jobs' work in flight" and "no more than thirty calls in flight" are different claims, and a test that counts calls cannot prove the first. State the unit in the spec and assert both. <spec review caught it; the test would have passed whatever the code did>
- cand: a numeric field typed from the spec's example rather than from real data will overflow on a production sentinel - an "unlimited" plan limit of 9999999999 did not fit an Int, the deserializer threw, a `runCatching` swallowed it, and a whole feature silently did not render while everything around it looked right. Type a server-chosen number at its widest, and treat any silently-empty optional UI as a parse failure until proven otherwise. <mobile client over a REST subscription endpoint; found only by looking at the device>
- cand: the same wrong import came back in the next work package - an implementer that cannot compile has no feedback loop, so it repeats its own mistakes across sessions. Put the specific compile errors of the previous WP in the next WP's implement prompt; the one that was listed was avoided, the one that was not was repeated. <KMP/Compose, two consecutive WPs, same internal `weight` import>
- cand: a test double added by a fix round is invisible to the next spec - the spec named the one fake it knew about and a second, newer one broke the build. Before writing "update the fakes", grep the test sources for every implementor of the interface. <KMP multi-module; one compile round>
